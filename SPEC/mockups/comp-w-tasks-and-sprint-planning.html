Tasks need a home, and a sprint should be filled from it

Under Board References a task is a card on a work board (for example Implementation). Today a task is born only inside its parent idea's drawer, a sprint is created from a bare form, and nothing links the two: a sprint cannot be filled from the tasks still waiting. This comp proposes one new surface and one new step.

Recommendation. Give every work board a Backlog tab (the home for tasks nobody has scheduled) and a Sprints tab, beside the existing Board. Creating a sprint ends with a picker of unassigned tasks. The same picker serves "Add tasks" on an existing sprint. Reasons and the alternatives I weighed are on screen 1, frame C.

Backlog = tasks on this board with no sprint (sprintId=none, a read the contract already has). Standalone cards, which the spec allows, finally have a place too.

The tabs sit on the board page, so a board with sprints off shows Board | Backlog only. Sprints appears when an Org Admin switches sprints on for the board (existing boards.sprints_enabled).

BWhat the Backlog tab does not replace

The parent's drawer keeps its Tasks section and "+ Add task" (a task made there is a task of that idea). The Backlog tab is the cross-idea view and the place to add a task that belongs to no idea or to several ideas' worth of planning at once. Both routes make the same card.

CWhere else tasks could live decision for the owner

1 · Backlog tab per work board (recommended)

  • Matches the model: a task is a card on a board, sprints are per board.
  • The picker for a sprint is just this list, filtered.
  • Board and Backlog stay one click apart.

Cost: to see all tasks across boards you visit each board.

2 · A global "Tasks" item in the sidebar

  • One list across every work board, good for "my tasks".
  • Sprints are per board, so the sprint picker still needs a board filter.

Cost: a second place for the same cards; I would add it later as "My tasks" on Home, not now.

3 · Keep tasks only inside the parent drawer

  • Today's behaviour.

Cost: no standalone or bulk planning; this is the gap you named.

BPicker or split view?

Use the drawer picker for create, the split view for planning

  • Create is a quick act: name, dates, tick tasks, done.
  • Planning a sprint is a longer act: you compare backlog and sprint side by side and see counts change.
  • Both read the same two lists, so the build is one list component and two layouts.

Only the drawer picker

  • Smallest build.
  • You cannot see what you have already put in the sprint while choosing more, beyond a count.

EQuestions this comp leaves open

  1. May a User add a standalone task, or only an Org Admin? (Screen 2)
  2. May a User add tasks to a sprint, or only an Org Admin? (Frame D)
  3. Should the Backlog also show tasks in a Completed sprint that were returned unfinished? (I assume yes: they are unassigned again.)
  4. Do you want a cross-board "My tasks" later? (Screen 1, frame C, option 2)
