The column is a cover, not a partition. 18 ≠ 16 — so every total on every roadmap surface has to print its distinct-count beside it or overstate the work.

What you get

  • Work that serves two goals is recorded as serving two goals. No arbitration, no fiction.
  • No incentive to raise duplicate issues, so provenance stays intact — the reason this feature exists.
  • An outcome’s issue list is the honest answer to “what advances this?”
  • Reflects how quarterly goals actually overlap rather than how a database prefers them to.

What it costs

  • Every total needs a distinct-count beside it. Miss one surface and the roadmap overstates the work.
  • Derived spans smear: a shared issue drags an outcome’s bar into a quarter its own work does not start in.
  • One issue completing moves two progress bars, so “done” is a per-view fact, not a per-issue one.
  • A join table, dedupe in every rollup query, and a defined empty case (last outcome removed → Not grouped).
  • Outcome becomes a chip list, so it cannot share the sprint picker’s visual grammar on the issue page.

What this option is betting

That accuracy about overlap is worth the arithmetic tax — and that the tax is payable, because it is one rule applied consistently: never print a total without its distinct-count.

The bet fails if that rule is applied unevenly. A single surface showing a bare sum is worse than single-parent, because it is confidently wrong rather than merely simplified. If this option is chosen, the distinct-count belongs in the query layer so no view can omit it.

Migration note: multi → single later is lossy — a human has to choose which grouping survives for every shared issue. This option is the harder one to reverse.
