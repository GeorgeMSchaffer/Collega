View As — behavior & security model

The comp is cheap to change; the rules below drive the backend and are the part to sign off on. Bracketed items are open decisions.

What it is

A privileged user temporarily browses Collega as another user — same role, same organization scope, same visible data — to reproduce issues, verify permissions, and support users. It is not a login as that user (no password, no session for them) and not a permanent role change.

Who can impersonate whom enforced server-side

  • Site Admin → any user in any organization.
  • Org Admin → active users in their own organization only.
  • User / Read-Only → no access; the control is hidden and the endpoint refuses them.
  • Suspended / archived users are listed but not selectable.
D-SCOPE — Can a Site Admin view as another Site Admin?

Site Admins have no organization, so view-as mostly makes sense for org users; impersonating a peer Site Admin has little support value and more risk.

Recommendation: exclude other Site Admins from the picker for MVP. Easy to relax later.

What you can do while viewing-as

D-MODE — Read-only preview, or full act-as?

Read-only: you see everything as them, but every mutating control is disabled. Safest; covers "why can't they see X / does their board look right?".

Full act-as: you can also perform actions, recorded with dual attribution. More powerful, larger blast radius.

Recommendation: ship read-only first (fast, low-risk, satisfies "view the app as another user"); add opt-in act-as later behind the same dual-audit trail.

Audit & accountability non-negotiable

  • Starting and exiting view-as each write an audit event (real actor + target user + timestamps).
  • If act-as is enabled, every mutation is stamped with both the real admin and the impersonated user — e.g. Sam Sitewide via view-as on behalf of Noah Contributor.
  • The impersonated user's own trail is never forged to look self-authored.

Session mechanics

  • Server-issued, scoped view-as context tied to the admin's real identity — not a re-login, not a token for the target.
  • Time-boxed (auto-expires) and one-click exit back to the admin's own identity; the banner is always visible and can't be dismissed without exiting.
  • Non-nestable — you can't view-as from within a view-as.
D-EXPIRE — Auto-expiry window?
Recommendation: 30 min idle, hard cap 2 h — mirrors the existing session-timeout feel.

Placement

D-PLACE — Where does the entry control live?

The request said "top nav bar, right-aligned," but Comp C deliberately dropped the top bar (the rail's avatar owns identity). Options: (a) a right-aligned View as… control in the page header — shown in the demo; (b) an item in the rail avatar menu.

Recommendation: page-header control (a), and also add it to the avatar menu — no reintroduced global bar.

Out of scope

Impersonation across a future SSO/OAuth boundary, and consented "request access" impersonation. Post-MVP.
