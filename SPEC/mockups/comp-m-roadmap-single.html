The column is a partition. Rows sum to the delivery set, so a total is a count and nothing needs a footnote.

What you get

  • Every roadmap number is a plain count. No distinct-count beside any total, ever.
  • “3 of 4 done” is a fact about the outcome, not about one of several overlapping views.
  • Derived spans form a clean staircase — an outcome’s bar covers only its own work.
  • One nullable FK (ideas.outcome_id). No join table, no distinct-count queries, no dedupe in any rollup.
  • “Which outcome is this for?” always has one answer, so nobody has to arbitrate a list.

What it costs

  • Work that genuinely serves two goals must be filed under one, and the roadmap then records a fiction.
  • Moving an issue silently drops another outcome’s count — an outcome can read as finished because its dependency was reassigned, not completed.
  • Teams route around it: duplicate issues get raised so both outcomes can claim the work, which is exactly the provenance loss this feature exists to prevent.
  • The forced choice is invisible after the fact. Nothing records that CLG-114 also served intake.

What this option is betting

That an honest, un-footnoted roadmap is worth more than an exactly accurate one — and that when work genuinely serves two goals, naming the primary one is a useful discipline rather than a lie.

The bet fails if teams start raising duplicate issues to get around the single slot. Watch for that: it is the specific failure mode, and it converts a modelling shortcut into the provenance loss this whole feature was built to stop.

Migration note: single → multi later is a cheap forward migration (copy the column into a join table, drop the column). This option is the reversible one.
