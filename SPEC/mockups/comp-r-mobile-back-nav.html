Mobile back navigation

On a phone there is no sidebar, so a detail screen needs a way up. Three options, each shown at 390px on the same three screens: a board, an idea in the drawer over that board, and a nested settings record. Today's topbar (components/nav/topbar.tsx) renders the trail as text, and only the board page links its parent.

In every option, back goes to the parent route, never history.back(): a link opened from an email or the inbox gets the same, predictable way up. The menus are live; tick "Show tap targets" to see each 44px hit area.

ABack chevron + page title

One step up, always. The trail is hidden under md; the title is the current page.

Back goes to

  • Board → /boards
  • Drawer → the board, /boards/pay-q4 (drops ?idea=). The chevron replaces the drawer's × on mobile: same destination, one control.
  • User record → /settings/users (People), not /settings

Accessibility

  • An <a>, not a button: it navigates, so long-press and open-in-tab work. 44×44 hit area around a 20px chevron.
  • aria-label="Back to {parent}", naming the destination, not just "Back".
  • Kept inside <nav aria-label="Breadcrumb">; the title carries aria-current="page". The page's one <h1> stays in PageHeader.
  • In the drawer, focus returns to the card the idea was opened from.

Trade-off

  • Smallest, most familiar; title gets the full width.
  • Only one level at a time: from a user record, Settings is two taps.

BTappable breadcrumbs, middle collapsed

Today's trail with every parent a link. When it overflows, the middle crumbs fold into "…".

Back goes to

  • Any crumb jumps straight to that route: /boards, /settings, /settings/users.
  • Drawer → the board, from the "…" menu or the × (drops ?idea=).
  • Collapse rule: keep the root and the current page; fold the middle into "…" only when the row overflows. The current page truncates with an ellipsis last, never below the key (CHK-12).

Accessibility

  • <nav aria-label="Breadcrumb"><ol>, current crumb aria-current="page", separators aria-hidden.
  • Each crumb link and the "…" button is 44px tall (and "…" 44px wide), with padding, not just its text.
  • "…" is a <button aria-label="Show N hidden levels" aria-expanded>; Esc closes it and returns focus.
  • CSS truncation keeps the full name as the link's accessible name.

Trade-off

  • Same pattern as desktop; any level in one tap.
  • Small text targets side by side; in the drawer the most useful crumb (the board) hides behind "…".

CCombination: back chevron + path menu

A's chevron for one step up; the title is a button that opens the whole trail.

Back goes to

  • Chevron: the parent route, as in A (/boards; the board; /settings/users).
  • Path menu: any ancestor in one tap, e.g. /settings from a user record.
  • Drawer: chevron replaces the ×; the menu's board entry goes to the same place.

Accessibility

  • Back link as in A: 44×44, aria-label="Back to {parent}".
  • Title is a <button aria-haspopup aria-expanded>, 44px tall; menu items are 44px links, the current one aria-current="page".
  • Both sit in <nav aria-label="Breadcrumb">; the small parent line is visible context, so the trail is never hidden from sighted users.

Trade-off

  • Big targets, full trail on demand, parent always visible.
  • Most to build; the title-as-button is less discoverable than visible crumbs.

Common to all three · open questions for the owner

  • Under md only (the sidebar's breakpoint); at md and up the current topbar trail stays, with its parent segments made links either way.
  • "Parent" is a route, not history: every Topbar caller passes its parent href and label, so a deep link and a sidebar visit get the same back.
  • Top-level pages (Boards, Ideas, Settings) have no parent: the left slot holds the mobile menu button instead.
  • Open: should desktop show the back chevron too? Does C's path menu earn its build cost over A?
